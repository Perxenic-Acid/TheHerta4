## Automated releases

TheHerta4 publishes an installable ZIP from each push to `main` with
`.github/workflows/release.yml`. Version numbers are
`vMAJOR.MINOR.PATCH`:

- Ordinary pushes increment only `PATCH`. The next version after `v4.1.50`
  is `v4.1.51`, then `v4.1.52`, and so on.
- To create a manual minor release, choose **Actions → Package and release
  TheHerta4 → Run workflow** on the `main` branch. The workflow bumps
  `MINOR` and resets `PATCH` to zero; optionally provide a higher
  `next_minor` to skip ahead. `MAJOR` is inherited from the latest Release.
- Version allocation uses existing published semver Releases, not the
  `bl_info` version in the source tree.
- Automatic publishes are normal GitHub Releases, so
  `releases/latest` and the in-addon updater can find them.
- The ZIP has a root `TheHerta4/` folder with the versioned
  `__init__.py`. The version field is injected *inside the packaged ZIP*,
  without committing a version-only change to `main`.
- The in-addon updater reads Release assets rather than GitHub's autogenerated
  tag source snapshots. Installing one of those source snapshots manually
  will retain the source tree's static `bl_info` version.
- A failed package build does not create a Release. Each successful run retains
  its ZIP as an Actions artifact for 30 days.

For a major-version transition, publish an explicit GitHub Release with a
higher `MAJOR`, or update this workflow's version policy deliberately.
If rapid pushes exceed GitHub Actions' concurrency queue capacity, GitHub
may supersede pending runs; release numbers then advance per completed
publish, rather than guaranteeing one release per skipped pending run.
